# fm-eval

## Goal
Measure how well Apple's on-device Foundation Model (via the Python SDK,
`apple-fm-sdk`) completes small, realistic coding tasks in existing
codebases when given ideal ("oracle") context. This is a validation gate for
a future on-device coding agent harness, so the numbers and failure
categories are the deliverable, not polish.

## Environment
- Python SDK lives in `.venv/` (apple-fm-sdk 0.2.1). Run with `.venv/bin/python`.
- Model context window: 8192 tokens, shared by prompt and output
  (`SystemLanguageModel().context_size`). Count tokens with
  `await model.token_count(prompt)`, not character estimates. Verified:
  plain prompts overflow at ~8100 counted tokens. Go is ~2.8 chars/token.
- `/usr/bin/fm` is a separate built-in CLI (`fm serve` exposes a Chat
  Completions API). Not used in v1, but keep the model call behind one small
  function so a different backend can be swapped in later.
- `fm serve --port N` works (checked 2026-10-10): OpenAI-style
  /v1/chat/completions, model id `system`, loopback only, ~1.3s for a tiny
  function. It streams even when the request does not ask for streaming.
- No custom adapters (checked 2026-10-10): Apple's adapter training toolkit
  ends at 26.0.0 and is "not compatible with ... 27 and later"; Apple
  staff on the developer forums: "no longer supporting adapters as of OS
  27". Neither the Python SDK nor the fm CLI exposes adapters.
- Toolchains: Go 1.25, Node 24 (runs `.ts` natively, `node --test`),
  cargo, Swift 6.4.

## Languages
One fixture per language, same conventions and roughly the same tasks, so
results compare across languages. Order:
1. Go (primary, full task set)
2. Python (full task set)
3. TypeScript (full task set)
4. Swift (about 8 core tasks)
5. Rust (about 8 core tasks)

Finish Go through checkpoint 3 before starting any other language.
Python port (2026-10-05): fixtures/python mirrors the Go fixture as flat
stdlib modules (respond, request, server with a tiny Router, ids, *_store,
*_handlers, testutil) tested with unittest subTest tables; run with
`python3 -m unittest discover -p "test_*.py"`. Same 18 tasks as `py-*`.
format_id lives in ids.py (to avoid a circular import). Python has its own
merge (harness.python_merge, same rules as gomerge), repair (import fixer)
and wiring. Not yet ported to Python: goapi (--skill auto).
Fixtures are stdlib only. Where a stdlib lacks HTTP or JSON (Rust), handlers
are plain functions over the fixture's own request and response types.

## Layout
- fixtures/<lang>/   Small repo per language. Must build and pass its tests.
- tasks/<lang>/      One TOML file per task.
- hidden/<lang>/     Tests used for grading. Never shown to the model.
                     hidden/<lang>/mutants/ holds broken files for
                     test-writing tasks.
- solutions/<lang>/<task-id>/  Hand-written correct target per task.
- harness.py         Task loading and grading, shared by the scripts below.
- verify_tasks.py    Each solution must pass and the untouched fixture must
                     not. Run it after adding or changing any task.
- run_eval.py        The runner.
- retry_ab.py        Compares retry styles starting from the same recorded
                     first attempts, after applying the current harness
                     (merge, repair, wire) to seeds and retries alike.
- regrade.py         Regrades recorded outputs after a harness fix.
- tag_failures.py    Heuristic failure tags per config and tier; spot-check
                     with --show TAG before trusting the counts.
- skills/            Skill files for `--skill` (repeatable; `auto` adds an
                     API reference generated by tools/goapi). go-shop-api.md
                     is the hand-written cheat sheet; go-shop-conventions.md
                     holds only conventions a generator cannot derive.
- tools/goapi/       Generates a compact API reference from a Go package.
- tools/gomerge/     Merges a snippet of Go declarations into a file, for
                     `--edit-format symbol`.
- results/           Timestamped JSONL output per run.

## Fixture spec
- 4 to 6 resources (users, orders, products, etc.) with consistent conventions:
  in-memory store, shared JSON response and error helpers, HTTP handlers,
  table-driven tests.
- Conventions should be distinctive enough that "follow the existing style"
  is a meaningful instruction.
- Leave gaps the tasks will fill (e.g. orders has a store but no GetOrder handler).
- Keep files small (roughly 60 to 150 lines) so a target file plus its
  context fits comfortably in the window with room for output.

## Task format (TOML)
id, lang, kind, tier, instruction, context (list of fixture paths,
hand-picked), target (single file the model writes), hidden_test (path in
hidden/<lang>/), test_cmd. Test-writing tasks have no hidden_test and
instead list `[[mutants]]` with `file` (under hidden/<lang>/) and
`replaces` (fixture path). Optional `mutant_test_cmd` runs only the
model's tests against mutants, for when existing tests would catch them.
- kind is `new_file` (target does not exist yet) or `modify` (target exists
  and the model must keep its existing code). Include a mix of both.
- test_cmd runs the whole package's tests, not just the hidden test, so
  collateral damage to neighboring code counts as a failure.
- Hidden tests call handlers directly, so every task is a single-file edit.
- Hidden test helpers use a `hidden` prefix to avoid clashing with names the
  model defines.

## Task tiers
- Easy: mirror an existing handler for a new resource.
- Medium: validation, query params, pagination, error cases.
- Test-writing: model writes a test file. Graded by running it against the
  correct implementation (must pass) and a deliberately broken one (must
  fail). Against the broken one it must compile and fail on an assertion;
  a compile error does not count as catching the bug.

## Runner rules
- Check `fm.SystemLanguageModel().is_available()` first.
- Copy the fixture to a temp dir per task. Copy the hidden test next to the target.
- Fresh `LanguageModelSession` for every attempt. No transcript buildup.
- Output mode `--output plain|guided`, default plain. Plain asks for the
  file as text; the runner strips markdown fences and echoed `=== path ===`
  delimiters and records what it removed. Guided uses a `@fm.generable`
  class with one `content: str` field. Finding (2026-10-05, SDK 0.2.1):
  guided generation of a full source file runs away until the context
  window overflows (~140s), even with maximum_response_tokens set and with
  tabs replaced by spaces, while the same prompt in plain mode finishes in
  ~18s. Guided works for tiny files only.
- Set sampling explicitly (recorded in the run header) so `--runs N`
  variance is meaningful.
- Up to 3 attempts (`--attempts N`). `--retry-style` (default `fresh`) sets
  what retries see: `full` (previous attempt plus raw log tail, the
  original baseline), `annotated` (error summary first, previous attempt
  with failing lines marked), or `fresh` (original prompt plus error
  summary, previous code not shown), or `diagnostic` (fresh plus
  `harness.diagnose`: likely causes with codebase facts, such as real
  signatures and usage lines, where a name is defined, unregistered or
  dropped routes, existing tests that broke). Error summaries come from
  `harness.summarize_failure`. `patch` shows the previous attempt plus
  summary and diagnosis and merges the reply (only changed declarations)
  into the previous attempt via harness.merge_into, so correct parts
  cannot be re-broken. If a retry prompt would not fit, trim
  context files before trimming the error output.
- Finding (2026-10-05): with `full`, the model usually returns its previous
  attempt unchanged (6 of 8 greedy retries were byte-identical), and for
  modify tasks the original file is no longer visible, so dropped code
  cannot be recovered.
- Finding (2026-10-05, retry_ab.py, 16 failed first attempts x 3 styles x
  up to 2 retries): 0/48 rescued under any style, with or without the
  fixer. Caveat: this was generic error feedback (what broke, not why) on
  raw failures, before skills, merge, repair, and wiring existed.
- Finding (2026-10-10, retry_ab.py on the best Go and Python configs with
  the current harness on seeds and retries; 58 first attempts still failing
  after the harness, up to 2 retries): fresh rescues 7/58 (12%),
  diagnostic 6/58 (10%); on the 38 seeds with a diagnosis, 2 vs 3. Retries
  now work somewhat, but diagnosis adds nothing measurable. The model does
  apply the diagnosed facts (s.reviews, router.handle, ok checks all
  appear), but each full rewrite introduces new, different errors
  elsewhere, so attempts do not converge. Approximate pass-with-feedback
  with fresh retries: Go 27/54 (50%), Python 30/54 (56%).
- Finding (2026-10-10, same 58 seeds): patch rescues 1/58 vs fresh 6/58
  (fresh reproduced its ~11% rate). 40/115 patch replies were identical or
  near-identical copies of the broken previous attempt, and 96/115 returned
  the whole file despite being asked for changed declarations only.
  Showing the model its previous code anchors it. Best retry: fresh
  regeneration with a short error summary; diagnosis and patching add
  nothing. `fresh` cuts verbatim copying (4/32 vs 13/32 for `full`) and
  `annotated` moves more failures from build to test stage, but neither
  produces a pass. On go-order-get, 16/16 generations (first attempts and
  retries, every style) deleted the existing routes.
- Every attempt is also graded after the language fixer (goimports for Go)
  and logged as `fixup_status`, and after `harness.repair` (brace balancing,
  goimports, unused variables blanked to `_`, compiled without hidden
  tests) as `repair_status`. `--fixup` or `--repair` makes that version the
  one that is graded and fed back.
- Python repair is a static import fixer (harness.python_fix_imports): names
  used but never bound that one fixture module (or a known stdlib module)
  defines get imported.
- Python results (2026-10-05, 18 tasks x 3 runs, first attempts; results/
  20261005-212410 and -214103): baseline 16/54 (30%) vs Go 10/54; with
  skills/py-shop-api.md 17/54, 22/54 (41%) after repair. The top Python
  failure is forgetting to import fixture helpers (the skill increases
  helper use, so it raises these until repair fixes them). The same 9 tasks
  fail in both languages: all new handler files, all but one test-writing
  run, order-cancel, both query filters, user-lookup.
- Hard-core analysis (2026-10-06): the 9 tasks that fail in both languages,
  54 failures after repair, read by hand:
  - 21 wrong use of an API that is in context or the skill: Go return
    values ignored, Python attribute names from priors (s.review_store,
    ReviewStore.list), invented helpers (CODE_OK, write_conflict,
    router.add_route), unittest subTest misuse.
  - 11 new code never wired in: handler written but route not registered
    (user-lookup 6/6), or a new parallel function added instead of editing
    the existing handler.
  - 9 misread spec: filtering on whether a status is valid instead of the
    ?status= value, wrong in_stock semantics, map[string]int with "ok".
  - 3 wrong expected values in tests (cannot predict formatID output).
  - 3 delegation: imports the handler it was asked to write from another
    module. 3 copied a declaration from the generated API sheet. 2 dropped
    existing code. 2 other.
- `--wire` (2026-10-06): handlers nothing references get their original
  route restored, or the model is asked one tiny guided question for the
  route (an enum of routes named in the request when there are any; regex
  guides are unsupported on SDK 0.2.1, and json_schema needs "x-order").
  Offline on recorded outputs, repair + wire: Go hybrid 23/54 (43%), Go
  baseline 20/54 (37%), Python skill 24/54 (44%), no regressions.
- Python merge (2026-10-06): offline on recorded outputs with repair + wire,
  full_merge lifts Python + skill from 24/54 to 27/54 (50%); the rewrite
  had dropped CreateUserRequest in all 3 user-lookup runs. full and
  full_merge send identical prompts, so these offline numbers equal a live
  run on the same samples.
- Best configs so far (pass@1, 18 tasks x 3 runs): Go 23/54 (43%) with
  full_merge + auto + conventions + repair + wire; Python 27/54 (50%) with
  full_merge + py-shop-api skill + repair + wire.
- Negative result (2026-10-06): a did-you-mean rename repair (unknown
  attribute or identifier -> closest valid name) fired 7 times on recorded
  outputs and rescued 0: each renamed call was still wrong (missing
  arguments, wrong logic) and 2 renames were semantically wrong. Wrong
  names reflect a wrong model of the code, not typos. Removed.
- Finding (2026-10-05, offline on the checkpoint 5 outputs): repair lifts
  pass@1 to 19/54 (35%) for both full_merge configs, 14/54 for baseline, no
  regressions. Brace balancing alone rescues go-user-store-update-name 9/9.
- Catch model errors (context overflow, guardrails, refusals) and record them
  as `model_error` with the error type and prompt token count.
- Kill `test_cmd` after a timeout and record it as `timeout`.
- Log per attempt: status, prompt_tokens, gen_seconds, output, log tail.
- Log per run: OS build, SDK version, context size, sampling options.
- `--edit-format full|symbol` (default full). In symbol mode, modify tasks
  ask for only added or changed declarations, which tools/gomerge merges
  into the existing file (same name replaces, new names append, imports
  unioned, everything else kept). Unparseable output is `merge_fail`.
  Additive merge (both languages) keys calls in call-only functions on
  callee plus first argument, so re-registering an existing route with a
  new handler replaces that line instead of registering it twice.
  Symbol mode always uses the `fresh` retry style. gomerge drops snippet
  declarations that duplicate symbols defined in other package files.
- Findings (2026-10-05, first attempts, 4 runs per config):
  - skills/go-shop-api.md left pass@1 unchanged (4/20) but removed every
    hallucinated-API failure (14 to 0). Next: generate it from go/ast.
  - Symbol mode without the duplicate guard: 0/12 on modify tasks (the
    model echoes context declarations). With guard and skill: 4/12, same as
    full-file mode.
  - Adding one line to an existing function (a route in orderRoutes) fails
    in every mode: the model keeps the old routes and omits the new one, or
    writes only the new one. 1 pass in ~100 generations on the order tasks.
  - `--edit-format full_merge --merge additive` (model writes the full file,
    gomerge merges it and keeps existing lines of call-only functions like
    orderRoutes) plus the hand-written skill: 8/20, double every earlier
    config. go-order-get 4/4. Remaining failures: ignoring (T, bool) and
    (T, error) returns, unused imports, cancel route not registered.
  - `--skill auto` (generated by tools/goapi) instead of the hand-written
    skill: 6/20. It cannot list stdlib conventions, so r.URL.Path
    hallucinations returned (7 of 8 relevant failures) and routes went
    unregistered. Hybrid: `--skill auto --skill skills/go-shop-conventions.md`.
- Checkpoint 5 full run (2026-10-05, 18 Go tasks x 3 runs, first attempts;
  results/20261005-192026, -194056, -203213):
  - pass@1: baseline (full, no skill) 10/54 (19%); full_merge additive +
    hand skill 16/54 (30%); full_merge additive + auto + conventions
    16/54 (30%). The generated hybrid matches the hand-written sheet.
  - new_file tasks 0/18 in every config (3 handler files, 3 test files);
    modify tasks 16/36 with the harness levers.
  - Test-writing 0/27 overall: wrong expected values, syntax, imports.
  - Remaining top failures with levers: syntax (9, e.g. dropping the
    closing brace of the function before an appended one), type errors,
    return-value misuse, broke existing behavior, unregistered routes.
- Run tasks serially. Support `--runs N` to repeat each task for variance.
- Support `--lang` and `--task` filters.
- Print pass@1 and pass-with-feedback at the end, per language.
- Optional flag `--skill path/to/skill.md` that prepends a skill file to the
  prompt, so runs with and without a skill can be compared.

## Later (structure the runner for these, do not build in v1)
- `--edit-format search_replace`, if symbol edits leave gaps.
- Files larger than the context window. Real Go files can be huge, so the
  harness must lift only the useful parts: skeleton views (signatures and
  types, bodies elided), extracting the specific symbols a task touches,
  and pairing this with symbol-level edits since a full-file rewrite of a
  huge file is impossible. Add tasks whose target or context files exceed
  the budget and compare slicing strategies.
- Calibration run of the same tasks against a larger model, to separate
  broken tasks from hard ones.

## Build order (stop and report at each checkpoint)
1. Go fixture with all tests passing.
2. First 5 Go tasks plus hidden tests. Verify each hidden test passes against
   a hand-written correct solution before using it.
3. Runner. Run the 5 tasks.
4. Expand Go to 15 to 20 tasks across tiers and kinds.
5. After a full run, read failures and tag each one: convention miss,
   hallucinated API, syntax, logic error, dropped existing code, truncated
   output, fences or prose in output, guardrail refusal, context overflow.
   Summarize counts.
6. Port to Python, then TypeScript, then Swift and Rust (core subset).

## Style
- No em dashes in any prose, comments, or docs.
- Keep it simple. This is a measuring instrument, not a product.
